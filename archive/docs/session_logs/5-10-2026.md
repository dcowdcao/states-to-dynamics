## 1 · Fixed: per-move board reconstruction color flip

### Symptom

In `geometry_analysis/per_move_board_reconstructions/ground_truth/moves_XX-YY.png` and every per-reconstructor folder, the dominant piece color (dark filled ● vs. hollow ○) was flipping every single move. On move 10 most pieces would appear dark; on move 11 they would all appear hollow; on move 12 dark again — even though physical Othello rarely flips the majority color twice in a row.

### Root cause

`make_per_move_reconstructions.py` was building ground truth with Karvonen's `games_batch_to_state_stack_mine_yours_BLRRC`, which **intentionally multiplies the board state by `flip = +1 if i%2==0 else -1`** so the encoding is always from the active player's perspective ("mine = the player who just moved"). The renderer was then drawing class 2 ("mine") as a solid black piece and class 0 ("yours") as a hollow white piece *regardless of move parity*. Because "mine" alternates between physical-black (on even moves) and physical-white (on odd moves), every other rendered frame looked color-inverted relative to reality.

This was purely a visualization labeling bug — **all accuracy metrics were and remain correct**, because predictions and ground truth both lived in mine/yours space and the cell-wise comparison `pred != truth` is invariant under the 0↔2 swap.

### Fix (option 1 of the three I'd proposed)

Render the **absolute** board (white / empty / black), keep accuracy scoring in mine/yours space.

Concrete changes in `Runs_GPU/Main_Trained_Run_All_SAE/geometry_analysis/per_move_board_reconstructions/make_per_move_reconstructions.py`:

- New helper `to_absolute_LRR(state_LRR_mine_yours)` that applies `swap_yours_mine` only on odd-indexed time slices, converting mine/yours → absolute (`0 = white, 1 = empty, 2 = black`).
- `main()` builds `truth_abs_LRR = to_absolute_LRR(truth_LRR)` once and `pred_abs_LRR = to_absolute_LRR(pred_LRR)` per reconstructor, and passes those to `render_2d_figure_set` instead of the mine/yours stacks.
- Mistake masks (`pred_LRR != truth_LRR`) are still computed in mine/yours space; since the 0↔2 swap is a bijection applied identically to predictions and truth, the boolean mask is identical in both spaces and overlays correctly on the absolute board. Verified empirically with a random sanity check.
- `STATE_COLORS_2D`, `draw_board_2d`, and the figure legend updated from `yours/mine` to `white/black`. Added an `ABSOLUTE_STATE_NAMES` constant.
- Updated `Runs_GPU/Main_Trained_Run_All_SAE/geometry_analysis/per_move_board_reconstructions/README.md` "Visualization conventions" section to describe the absolute rendering and document the prior bug.

## 2 · New analysis: per-move L0 sparsity

Folder: `Runs_GPU/Main_Trained_Run_All_SAE/geometry_analysis/l0_per_move/`

### Goal

For each of the 7 SAEs, track how the **L0 sparsity** (number of features with non-zero activation per token) evolves with the **Othello game move number**, averaged across many real games. Question being answered: how does the SAE's load on the residual stream ramp up as the board fills, and where does each SAE plateau?

### Method

Implemented in `make_l0_per_move.py`:

1. Stream `N_GAMES = 200` games from `taufeeque/othellogpt`, take first 59 tokens of each (matches `CTX_LEN` used at SAE training).
2. Run Othello-GPT in batches of 8, capture `blocks[5].hook_resid_post` → `[200, 59, 512]` activation tensor.
3. For each SAE: standardize with the SAE's saved `(mean, scale)`, encode, count `(features > 0)` per token → reshape to `[200, 59]` → aggregate per move index (mean, median, p25, p75, std).

L0 definition: `(sae.encode(x_std) > 0).sum(dim=-1)` per token.

- ReLU-based SAEs (Standard, PAnneal) and Gated/GatedAnneal: encoder output is non-negative, `> 0` is standard L0.
- TopK selects 80 indices per token by construction, but applies ReLU before top-k, so a top-k slot can hold a 0 when fewer than 80 post-ReLU activations are positive. The `> 0` count therefore caps at 80 and dips below it on OOD tokens.
- SpaDE uses sparsemax → exact zeros, `> 0` is correct.

CPU runtime: ~3 min total.

### Headline numbers (200-game means)

| SAE | grand mean L0 | move 0 | move 58 | per-move max (move) |
|---|---:|---:|---:|---|
| Standard      | 1090.09 | 9.25  | 1269.92 | 1300.67 (m48) |
| SpaDE γ=1e-04 |  963.22 | 2.00  | 1048.86 | 1058.74 (m8)  |
| PAnneal       |  338.92 | 2.79  |  416.62 |  433.90 (m57) |
| SpaDE γ=1e-02 |  136.83 | 1.00  |  160.71 |  181.88 (m57) |
| TopK          |   79.93 | 76.06 |   80.00 |   80.00 (m3)  |
| Gated         |   50.22 | 1.61  |   48.81 |   63.16 (m48) |
| GatedAnneal   |   32.46 | 2.22  |   22.99 |   39.30 (m38) |

### Observations

1. **Sharp ramp-up over the first ~5 moves, then plateau.** Every SAE except TopK starts at L0 ≈ 1–10 at move 0 and reaches steady state by move ~5. Move 0 is OOD-adjacent: only one move of board state to represent.
2. **Three sparsity regimes across ~3 orders of magnitude.** Dense (Standard, SpaDE γ=1e-04 ≳ 1000), mid (PAnneal, SpaDE γ=1e-02 ≈ 100–500), sparse (TopK = 80, Gated ≈ 50, GatedAnneal ≈ 32). Standard is effectively using ~1/8 of its 8192-dim codebook per token at steady state.
3. **TopK is not flat at 80 on moves 0–2** (76.06, 79.21, 79.83). The encoder always selects 80 indices, but post-ReLU activations at OOD early tokens contain fewer than 80 strictly-positive entries, so the count of `>0` features dips. Real OOD signal; documented in the script as a soft assertion rather than a hard failure.
4. **Late-game decline is unique to Gated and GatedAnneal.** Both peak around moves 38–48 and shed features as the board fills toward 60 stones. Consistent with GatedAnneal's annealed penalty being most active on dense late-game activations.
5. **SpaDE γ sweep is steep.** 1e-04 → 1e-02 cuts steady-state L0 from ~960 to ~135 (7× compression for 100× change in penalty strength).
6. **Move 0 is a universal degenerate.** Every SAE collapses to tiny L0 at the first token. Cross-references with the per-move reconstruction analysis: every SAE also gets 0/1 on the changed-cell metric at move 0. Same OOD phenomenon, two views.

## 3 · New analysis: 2D PCA + UMAP of per-square feature directions

Folder: `Runs_GPU/Main_Trained_Run_All_SAE/geometry_analysis/embedding_pca_umap/`

### Goal

For each reconstructor (7 SAEs + LinearProbe), build a 2D embedding of the **60 non-center Othello squares** to see whether the per-square representation has discernible geometric structure (corner / edge / interior, etc.). One point per square; 4 center squares excluded.

### Interpretation of "per-square embedding"

For each reconstructor we build a `[60, 512]` matrix. For each square (r, c), the 512-dim row is computed as follows:

- **SAEs.** From the precomputed `f1_TFRRC.pt`, pick `best_feat[r, c, s] = argmax over features of max-over-thresholds F1` (same per-(square, class) pick used by `make_per_move_reconstructions.py`). The "direction" associated with that feature is the SAE's **decoder column** `decoder.weight[:, best_feat[r,c,s]]` (or `Ad[:, best_feat]` for SpaDE) — the vector this feature writes into the residual stream when active. Average those 3 per-class directions to get the per-square embedding.
- **LinearProbe.** The probe is `[D=512, 8, 8, 3]`. The per-square embedding is `probe[:, r, c, :].mean(dim=-1)`. No label permutation needed (averaging is class-order-invariant).

Rationale for averaging across class: each square's three per-class directions are the reconstructor's three "answers to which state is at this square" — averaging them collapses the *state* axis and leaves a pure *spatial* readout. PCA/UMAP of these centroids tests whether squares cluster by board geometry.

### Method

Implemented in `make_embedding_pca_umap.py`:

1. Per SAE, load via `load_karvonen_sae`, read decoder weight, read `f1_TFRRC.pt`, compute `best_feat[r,c,s]`, gather + average → `[60, 512]`.
2. Linear probe: same shape gymnastics from `probe.mean(dim=-1)`.
3. `sklearn.PCA(n_components=2)` per matrix.
4. `umap.UMAP(n_components=2, n_neighbors=10, min_dist=0.1, metric='precomputed', random_state=0)`. Distance matrix precomputed with `sklearn.metrics.pairwise_distances(..., metric='euclidean')` to **sidestep an upstream UMAP × numba≥0.59 incompatibility** (`math.pow` / `math.ceil` attribute lookups removed from numba). `NUMBA_DISABLE_JIT=1` is set inside the script before importing umap; the pure-Python path is sub-second per fit with 60 points.

CPU runtime: ~30 s.

### PCA 2D variance explained

| Reconstructor       | PC1   | PC2  | sum   |
|---|---:|---:|---:|
| GatedAnneal         | 16.8% | 8.4% | 25.3% |
| Gated               | 14.0% | 8.5% | 22.5% |
| SpaDE γ=1e-02       | 10.8% | 7.2% | 18.0% |
| PAnneal             | 11.9% | 5.5% | 17.4% |
| TopK                | 10.9% | 4.6% | 15.6% |
| Standard            |  6.8% | 4.9% | 11.7% |
| SpaDE γ=1e-04       |  6.6% | 4.2% | 10.8% |
| LinearProbe         |  4.0% | 3.5% |  7.5% |

### Observations

1. **GatedAnneal has the most 2D-organized per-square representation** (25.3% explained). In its PCA panel, corners cluster together, X-squares pop out in their own region, interior squares form a tight blob.
2. **LinearProbe is the most diffuse in PCA** (7.5%). Its per-square directions live in a genuinely higher-dim subspace because the probe is trained jointly over all 512 dims rather than picking one feature per (square, class). UMAP rescues some structure (corners form a rough outer ring).
3. **The corner ↔ X-square dichotomy reappears across most SAEs.** Othello's strategically opposite pair (corners permanent / X-squares give the opponent corner access) separates in the SAE feature geometry, even though no SAE was told about Othello strategy.
4. **Standard SAE looks like noise in PCA but acquires structure in UMAP**, consistent with its very high L0 (~1090 mean) leaving its decoder directions barely constrained.
5. **Both SpaDE configs sit on the diffuse end of PCA**, with γ=1e-02 (18.0%) more organized than γ=1e-04 (10.8%) — same direction as the L0 trend.

### Color scheme

After the first cut used a categorical (corner / X / C / edge / interior) color scheme, the marker palette was switched to the **radial-magma** scheme already used in [`activations_pca_probe_overlay/`](Runs_GPU/Main_Trained_Run_All_SAE/geometry_analysis/activations_pca_probe_overlay/) for visual consistency. Each marker color follows `magma` clipped to `(0.15, 0.92)` over Chebyshev distance from board center, so non-center squares fall into three rings: `d=1.5` (12 squares, dark purple), `d=2.5` (20 squares, red), `d=3.5` (28 squares, orange). A horizontal magma colorbar with ring-distance ticks replaces the previous categorical legend; inner-ring labels are drawn white-on-purple, outer-ring labels black-on-orange. The `embeddings_60x512.npz` now stores `chebyshev_distance` (float per square) in place of the prior `categories` string array.

Under the radial scheme the reading question changes from "do strategic categories cluster?" to "does the 2D layout separate inner-ring from outer-ring squares?" Same conclusions hold: GatedAnneal, Gated, TopK, PAnneal show clearer ring-by-ring separation in both PCA and UMAP than the dense SAEs (Standard, SpaDE γ=1e-04); LinearProbe is the most diffuse under PCA but acquires ring structure under UMAP.

### Additional review notes (post-radial-color regeneration)

A more careful look at the radial-coloured PCA + UMAP panels surfaced five takeaways beyond the initial ones (full text in [`embedding_pca_umap/README.md`](Runs_GPU/Main_Trained_Run_All_SAE/geometry_analysis/embedding_pca_umap/README.md#additional-takeaways-2026-05-11-review)):

1. **The discriminating axis is consistently "outer ring vs everything else"**, never inner-vs-middle. The 28 perimeter squares segregate from the 32 interior squares in every panel that shows clustering; inner and middle rings are visually intermixed everywhere. Matches Othello's edge-vs-interior combinatorial asymmetry.
2. **Gated and PAnneal cluster by ring as cleanly as TopK in UMAP — sometimes more so.** The pattern is *discrete-sparsity SAEs (TopK / Gated / GatedAnneal / PAnneal) all stratify by ring; dense SAEs (Standard / SpaDE) do not*. TopK is striking but not unique — it's the family that organizes geometrically.
3. **PCA 2D variance explained does not predict ring-clustering quality.** GatedAnneal leads on variance (25.3%) but its ring split looks comparable to Gated (22.5%) and slightly less crisp than TopK's (15.6%). Variance fraction is mostly a function of decoder-column norm distribution under each training penalty, not of layout interpretability. Read the *shapes*, not the percentages.
4. **The two SpaDE configs differ visibly in UMAP**, corroborating the L0 finding: γ=1e-02 shows weak but real bias of outer-ring points toward one side; γ=1e-04 is uniformly distributed. SpaDE without enough sparsity penalty slides into the same "dense ReLU" regime as Standard and loses interpretable structure as a side effect of losing sparsity.
5. **Geometric organization rank ≠ board-reconstruction F1 rank.** Standard places 3rd on nonempty F1 but is one of the worst at ring clustering; GatedAnneal is the opposite. The two metrics measure different interpretability properties — F1 says "the SAE has some feature per (square, class) that classifies well", PCA/UMAP says "the whole dictionary is geometrically organized by board position". A high-L0 dense SAE can win F1 by brute force without organizing features spatially.

### Caveats

- PCA variance fractions are **not directly comparable across SAEs**: decoder norms differ wildly between SAEs because of different training penalties.
- UMAP with 60 points is at the small end of useful — `n_neighbors=10` is doing most of the local geometry, and global distances should be read loosely.
- Best-feature picks may be near-dead for some (square, class) combos; their decoder direction enters the per-square average anyway. A future extension could weight the average by the per-(square, class) best F1.

## Data-representation clarifications established this session

Two clarifying questions came up while explaining the pipeline; documenting answers here for future reference.

### Are empty squares represented in the input token sequence?

**No.** Othello-GPT's vocabulary has 61 token IDs: token 0 is a sentinel (`itos[0] == -100`) used for padding/pass; tokens 1–60 each correspond to one of the 60 playable (non-center) board squares. Each token in a real game means "the current player places a stone on this square". The model never sees an `empty` token. Empty cells exist only after the move sequence is decoded into an 8×8 board state by `OthelloBoardState.umpire(...)`.

### How are "my piece" vs "your piece" denoted in the input?

**They are not.** Color/player is implicit in **move-index parity**: in a normal pass-free game, black always plays first, so even-indexed tokens are black moves and odd-indexed tokens are white moves. The model has to learn this from training. Karvonen's `games_batch_to_state_stack_mine_yours_BLRRC` codifies the same parity rule by multiplying the board state by `flip = +1 if i%2==0 else -1` after the umpire runs. So "mine = the player who just moved" is enforced *after the fact* on the simulated board state, not via any input-side marker.

Edge case worth flagging — **forfeits**. Othello permits a forced pass; the engine handles this by silently flipping `next_hand_color`, but the mine/yours labeller uses raw token-index parity (`i%2`) and would mis-label whose perspective is "mine" for every move after a pass. The `taufeeque/othellogpt` dataset is conventionally filtered to length-60 pass-free games, so for the analyses run in this codebase the parity assumption holds — but if you ever evaluate on games with passes, mine/yours labels will silently drift.
